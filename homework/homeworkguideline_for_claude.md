# Homework PPT 제작 매뉴얼 (Claude용)

> 사용자가 **"가이드라인 지켜서 만들어줘"** 라고 하면 이 문서 전체를 기준으로 작업한다.
> 이 문서는 특정 프로젝트 기록이 아니라 **매 과제에 공통으로 적용되는 규칙**이다. 프로젝트가 끝나면 그 프로젝트에서 얻은 교훈만 일반화해서 여기에 반영한다 (§10).

---

## 0. 한눈에 보기

| 항목 | 기준 |
|---|---|
| 입력 | 사용자가 `homework/`에 올린 과제 PPT (슬라이드마다 요구사항이 적혀 있음) + Verilog 소스 |
| 출력 | `(프로젝트 제목)_정안성.pptx` → 사용자 검토·수정 반복 → 최종 **PDF** (`(프로젝트 제목)_정안성.pdf`) |
| 청중 | 디지털 설계 경력 30년차 임원진 |
| 핵심 기준 | 임원이 **딱 봤을 때 "아, 이런 식으로 잡아냈구나"** 가 보여야 한다 |
| 디자인 | 아기자기할 필요 없음. **가시성·가독성 우선**, 정보 전달이 목적 |
| 금지 | HTML 산출물, 슬라이드에 코드 조각, 사용자 `vfile/`에 쓰기, **부가 설명·주석 줄**, `?`·`~면`·`~다` 어미, 설계 용어 한글 번역 (§3-3) |

---

## 1. 작업 시작 절차

1. **과제 PPT 확인** — 사용자가 `homework/`(또는 `homework/<프로젝트명>/`)에 올린 PPT를 연다. 이 PPT가 유일한 출발점이다.
2. **요구사항 추출** — 슬라이드 텍스트를 모두 뽑아 슬라이드별 요구사항 목록을 만든다.
   - 요구사항이 적힌 부분은 **반드시 표현**한다 (빠뜨리면 안 됨).
   - 사용자가 사진을 편집해 붙인 슬라이드는 **바로 아래 슬라이드에 같은 원본 사진**이 있다 → 그 원본으로 깔끔하게 재구성한다. 사용자의 편집본은 "이렇게 구성하면 되겠구나" 하는 참고용이다.
3. **소스 확인** — 모듈 블록도·세부 동작은 실제 코드 기준으로 그린다. 참조 경로 우선순위:
   1. PPT/사용자가 알려준 경로
   2. 프로젝트 폴더의 `sim_file/`, `source_file/`, `constraint/`
   3. 없으면 `~/vfile/` (여기엔 다 있다)
4. **먼저 물어볼 것** (추측 금지)
   - 필요한 사진·캡처 (사용자가 구해서 첨부함)
   - **보드 사진의 입력값** — 사진으로 스위치 판독은 불가능하다. 처음부터 물어본다
   - 원본 PPT와 코드가 다를 때 어느 쪽이 맞는지 (§4-4)
   - 모르는 내용 전부
5. **덱 구성안 작성 → 제작** (§2, §3)

## 2. 덱 구성 표준

원본 PPT의 목차는 중구난방일 수 있다. 임원이 좋아할 **피라미드 구조(결론 → 근거)** 로 재배치한다. 요구사항에 없더라도 필요하다고 판단되는 슬라이드는 **반드시 추가**한다 (추가는 필수).

| 순서 | 섹션 | 내용 |
|---|---|---|
| 1 | 표지 | 주제, 이름. 표지 상단 태그는 `VERILOG · HOMEWORK` 형식 |
| 2 | Executive Summary | 무엇을 만들었고, 무엇이 문제였고, 어떻게 해결·검증했는지 한 장 |
| 3 | 개발 흐름 | v1 → v2 → v3 … 버전별 변경점·문제를 한 줄씩 |
| 4 | HW 이해 | 회로도·핀·타이밍 등 설계 전제 (회로도/보드 사진 위에 직접 표시) |
| 5 | 버전별 설계 | 포트 → 블록도 → 모듈 역할(예시 값 하나로 데이터 흐름 추적) → FSM 등 상세 |
| 6 | 버전별 검증 | TB 구조 → 시뮬레이션 파형 → 보드 출력 |
| 7 | 문제 원인·해결 | 증상 → 원인 → 수정 → 재검증 |
| 8 | 최종 결과 | 최종 블록도 + 보드 출력 사진 (입력값 명시) |
| 9 | **검증 방법론 평가** | §5 — Claude의 종합 평가 (필수) |
| 10 | 개선 제안 / 새 TB | 기존 TB 허점 → 해결, 새 TB 구조·채점 순서·타이밍·실행 결과 |
| 11 | 결론·고찰 | 설계 결과 / 기존 검증의 문제 / 교훈 |

- 슬라이드 하단에 페이지 번호 `N / 전체`. 슬라이드를 추가·삭제하면 **본문 속 페이지 참조(p.xx)까지 같이 고친다**.
- 사실이 바뀌면(예: 원인이 다른 것으로 밝혀짐) Executive Summary·개발 흐름·평가 점수·결론까지 **연쇄 수정**한다.

## 3. 슬라이드 작성 규칙 (매번 지킬 것)

1. **제목은 영어 결론 한 줄 (두괄식).** "—" 뒤 부연 설명을 붙이지 않는다. 예: `Simulation — 7 of 8 Switch Codes and Both Wraps Match`. 본문도 필요한 내용만 넣는다.
2. **슬라이드에 코드 조각을 넣지 않는다.** 단, **모듈 이름·디지털 설계 용어는 영어 그대로** 쓴다 (§3-3).
   - 모듈: `tick_gen`, `tick_counter`, `digit_splitter`, `Fnd_Controller` … — 블록도 **도형 안 이름까지** 영어 ("Tick 생성기" ✗)
   - 회로 요소: adder, MUX, comparator, register, inverter ("덧셈기·선택기·비교기·반전" ✗)
   - TB 내부의 임시 변수(예: `r_seen`)만 뜻을 풀어 쓴다. 결함은 번호 대신 **증상 이름**("천의 자리가 안 켜짐")
   - 한 번 정한 이름은 덱 전체에서 통일한다.
3. **그림으로 보여준다** — 미니 FND 화면, 체크표가 채워지는 단계, ✓ 잡음 / ✗ 놓침 표시, State 다이어그램(의도 vs 버그) 등.
4. **구조 설명은 2단** — 위: 실제 모듈 구성(코드 기준), 아래: 같은 번호로 쉬운 풀이.
5. **설명은 "어떤 모듈이 왜 이 출력을 냈는지" 중심.** 이유는 본문 안에 한 줄로 쓰고, 별도의 참고·해석·주의 박스로 빼지 않는다 (예: 시뮬레이션 클럭을 줄인 이유 = 실제 클럭으로 전수 검사 시 수 시간).
6. **사용자가 PPT를 직접 고친 부분(제목·문구·삭제·위치)은 다음 수정에서도 그대로 유지한다.** 작업 전에 항상 최신 PPT와 직전 버전을 비교한다. **사용자가 지운 슬라이드·문구·박스는 필요 없어서 지운 것 → 되살리지 않는다** (표지처럼 필수 슬라이드가 통째로 사라졌을 때만 확인).
7. 회로도·보드 사진은 **사진 위에 직접 라벨+지시선**으로 표시한다 (핀명, 버튼, LED 등).

### 3-1. 시뮬레이션 파형 슬라이드 (사용자 표시 방식)

- **한 장에 한 파형**, 슬라이드 폭 전체로 크게
- 관련 없는 행은 **어둡게 마스크** (약 77% 검정)
- 자리값·합 등은 파형 위에 **흰 라벨**로 직접 표시
- 입력 변경 경계는 **노랑/빨강 세로선**, 판정 시점은 주황 점선
- 확인할 신호 이름은 **연두색 박스**
- 모든 주석은 PPT 네이티브 도형으로 (§6) — 사용자가 위치를 직접 조정할 수 있게
- Tcl 콘솔 로그에 과도값(중간값)이 찍히면 그 이유를 해석하는 슬라이드를 둔다

### 3-2. 사실·숫자

- **원본 PPT보다 코드/XDC가 기준이다.** 원본과 다르면 코드 기준으로 고치고 사용자에게 정정 목록을 보고한다 (핀 번호, 인코딩 값, FSM 분류(Moore/Mealy) 등이 자주 틀린다).
- **숫자는 실측·리포트 값만 쓴다.** 추정·환산 수치는 슬라이드에 넣지 않는다 (§3-3). 시뮬레이션 시간 같은 값이 꼭 필요하면 작은 입력으로 실측해 환산한다 (과거에 "2~4일" 추정이 실측 4.9시간으로 틀렸던 적 있음).
- 사용자가 직접 밝힌 사실(예: "TB 없이 보드부터 올렸다")은 원인 분석·평가에 그대로 반영한다.

### 3-3. 문체·용어·부가 설명 — 반복 지적 사항 (제출 전 전수 검사)

> 매 과제마다 같은 지적이 반복됐다. 슬라이드 텍스트를 전부 뽑아 아래 패턴을 검색하고 0건이 될 때까지 고친다.

**문체 — 개조식 명사형으로 끝낸다**

| 금지 | 고친 예 |
|---|---|
| `?` 로 끝나는 문장, `~는가` `~나` | "각 클럭의 타이밍을 어떻게 맞추나?" → **클럭 타이밍 조절 방법** · "+5 ns는 왜?" → **+5 ns 이유** |
| `~다` 어미 (`한다` `된다` `이다` `하면 된다`) | "고르기만 한다" → **선택만 함** |
| 조건 `~면` (전부 금지) | "분주 클럭으로 돌리면" → **돌릴 경우** · "Tick을 쓰면" → **쓸 경우** · "방식이었다면" → **방식일 경우** |
| 불필요한 부사 (`정확히` 등) | 데이터가 있으면 **수치만** 쓴다 — "정확히 100 ms" → **100 ms** |
| 제목·소제목의 부연 | "Setup — 늦은 도착 검사" → **Setup** · "질문의 그림 — …" → 접두어 삭제 · "Tick 방식 (이 설계)" → **Tick 방식** |

**용어 — 디지털 설계 용어는 번역하지 않는다**
- Setup / Hold, Slack, **Negative Slack**, WNS · TNS · WHS, Skew, Glitch, Clock Enable, **Common Anode** ("공통 애노드" ✗), inverter ("반전(~)" ✗), adder · MUX · comparator · register
- 모듈 이름은 코드의 영어 이름 그대로 (§3 규칙 2)
- 상태·동작 이름은 영어 대문자: **UP · DOWN · STOP · CLEAR · HOLD** ("증가·감소·멈춤·초기화·값 유지" ✗)

**부가 설명 — 넣지 않는다 (사용자가 슬라이드마다 직접 지웠던 것들)**
- 슬라이드 하단의 한 줄 주석 ("원본 대비 수정: …", "Tick · 스위치 타이밍 — …" 등)
- "캡처 해석 (참고)", "어둡게 처리한 행", "주의 — … (추정)" 같은 보조 박스
- 표 옆의 설명 카드 → 표 위에 **표 이름만** (예: `Switch Action Table`)
- 범례 문구의 부연 ("순차 — 클럭 엣지에서 갱신" → **순차**)
- 추정·환산 수치 (예: "단순 환산 시 약 187 MHz") — 실측·리포트 수치만
- Executive Summary의 "남은 일 / 개선 제안" 박스, 표지의 장식 그래픽·참조 파일 박스
- 개념 슬라이드 끝의 "이 설계: …" 적용 줄

**개념 질문 슬라이드 구성** — 정의 → 왜 치명적인지 → 어떻게 발생하는지 → 어떻게 해결하는지. 내용이 많으면 슬라이드를 여러 장으로 나눈다 (예: Setup / Hold violation).

## 4. 사용자와의 수정 루프

1. PPTX를 만들어 검토를 받는다.
2. 사용자는 PPTX를 **직접 고치거나**, 슬라이드 위에 요청을 적어 돌려준다.
   - 요청 형태: `*`·`→`로 시작하는 문장, 구어체 메모, 새로 붙인 캡처 (예: `* 영어로(제목)`, `→ 이거로 바꿔줘`)
   - 텍스트를 전부 뽑아 이런 메모를 찾는다 → 반영 → **메모는 지운다**
   - 메모가 **문체·용어·부가 설명에 대한 지적**이면 그 슬라이드만 고치지 말고 **덱 전체에 같은 패턴을 검색해 모두 고친다** — 그리고 §3-3에 규칙으로 추가한다 (같은 지적이 다시 나오지 않게)
3. 이후 수정은 **항상 최신 PPTX를 직접 편집**한다. 처음부터 재생성해서 덮어쓰지 않는다 (재생성이 꼭 필요하면 먼저 확인).
4. 사용자가 캡처를 줄 자리는 **placeholder 박스**로 비워 두고, 어떤 구간을 캡처하면 되는지 알려준다. 받으면 교체하고 주석을 단다.
5. OK 사인 → 마무리 절차 (§9).

## 5. 검증 방법론 평가 (필수 섹션)

사용자가 수행한 검증에 대해 **Claude만의 종합 평가**를 넣는다. 디지털 설계 엔지니어가 납득할 기준이어야 한다.

### 5-1. 평가표

- 항목별 점수 + 근거 한 줄, 합계(예: /40)와 등급. 권장 항목:
  - 입력 커버리지 (전수/대표값, carry-in 포함 여부)
  - 기대값 독립성 (DUT와 같은 로직을 재사용하지 않는가)
  - 관측 지점 (내부 신호가 아니라 실제 출력 핀 기준인가)
  - 판정 타이밍 (과도값을 피해 안정 시점에 판정하는가)
  - 자동 판정·리포트 (err 카운트, PASS/FAIL 출력)
  - 보드용 Top까지 시뮬레이션했는가
  - 문제 해결 절차 (재현 → 원인 → 수정 → 재검증)
  - 문서화·재현성
- 점수는 결함 주입 결과(§5-2)를 근거로 매긴다. 사실이 바뀌면 점수도 다시 매긴다.

### 5-2. 결함 주입으로 증명

"이 TB가 버그를 잡는가"를 말이 아니라 **결과로** 보여준다.

1. RTL 사본에 현실적인 결함을 심는다 (carry 고장, 특정 자리 미구동, FSM 천이 누락, 순서 건너뜀, 두 자리 동시 ON 등 — 실제로 겪은 버그를 반드시 포함)
2. 원본 RTL + 결함 RTL 각각에 **기존 TB / 새 TB**를 돌린다
3. 슬라이드에는 결함별 ✓ 잡음 / ✗ 놓침 + 오류 건수를 그림으로

### 5-3. 새 TB 제안

- **기존 TB는 수정하지 않는다.** 새 파일(`*_v2.v` 등)로 만든다.
- 구조: Driver(입력) → DUT → Monitor(출력 핀 역변환) → Golden model(독립 기대값) → Checker + Report
- 슬라이드 흐름: 기존 TB 허점 N가지 → 해결 매핑 / 새 TB 구조(2단 설명) / 채점에서 확인하는 항목(예시 + 잡는 버그) / 채점 순서 그림 / 타이밍 / 실행 결과(사용자 Vivado 캡처)
- 시뮬레이션용 Top(빠른 클럭, 전수)과 보드용 Top(실제 분주기, 대표값 몇 개)을 나눠 검증하고 이유를 밝힌다.

## 6. PPTX 제작·편집 방법

- 텍스트·카드·표·다이어그램·주석은 **PowerPoint 네이티브 개체**로 만든다 (사용자가 직접 수정 가능해야 함). 사진·캡처만 이미지.
- 처음 생성: pptxgenjs (Node) 등 사용. 이미지 처리는 scratchpad에 `npm install sharp` (Python에 PIL/pip 없음).
- 이후 편집: unzip → `ppt/slides/slideN.xml` 직접 수정 → 재압축. WSL에 zip·pip가 없으므로 **Python `zipfile`** 로 압축. 좌표는 1280×720 px 기준 × 9525 EMU.
- 빌드 스크립트·가공 이미지는 scratchpad 또는 임시 `_build/`에 두고, 마무리 때 삭제한다.
- **QA**: Windows PowerPoint COM으로 슬라이드를 PNG로 내보내 눈으로 확인 (글자 넘침, 겹침, 라벨 위치). 임시 폴더(예: `C:\Temp\pptqa`)는 마무리 때 삭제.
- PDF 변환: PowerPoint COM `SaveAs(path, 32)` — **사용자가 마지막으로 고친 PPTX**로 만든다.

## 7. Verilog 파일 규칙

- Claude가 쓰는 sim/source 파일 위치: **`homework/<프로젝트명>/`** 아래 `sim_file/`, `source_file/`, `fault/`. **사용자 `vfile/`에는 쓰지 않는다.**
- 주석·`$display`까지 **영어(ASCII)만** — Windows Vivado 2020.2에서 한글이 깨진다.
- `fault/`(결함 주입 사본)는 원본과 **모듈명이 같으므로 Vivado 프로젝트에 넣지 않는다** (넣으면 대량 오류 발생). 사용자에게도 이 점을 알린다.
- Tcl 로그에 캡처하기 좋은 시각을 `[MARK]` 등으로 출력해 두면 사용자가 파형 캡처 위치를 찾기 쉽다.

## 8. 시뮬레이션 환경 메모

- 기준 시뮬레이터: **Windows Vivado 2020.2 xsim** — WSL에서 `cmd.exe`로 `xvlog` / `xelab` / `xsim` 실행 (실행 스크립트는 `fault/mk.sh`처럼 프로젝트 폴더에 둔다)
- Vivado GUI 기본 runtime은 1000 ns → 결과를 보려면 `run all` 안내
- Verilator(devel 버전)를 쓸 경우 최적화 버그로 에러 카운트가 0으로 남는 문제가 있었음 → **반드시 `-O0`**
- Chrome headless(`chrome.exe --headless=new`)로 렌더 확인 가능

## 9. 프로젝트 마무리 절차 (OK 사인 후, 매번 동일)

1. 최종 PPTX → **PDF 변환** (사용자가 마지막으로 고친 버전 기준)
2. 폴더 정리
   ```
   homework/<프로젝트명>/
   ├─ (프로젝트 제목)_정안성.pdf
   ├─ sim_file/     ← Claude가 만든 TB
   ├─ source_file/  ← Claude가 만든 RTL (있을 때만)
   └─ fault/        ← 결함 주입 사본 + 실행 스크립트 (Vivado 프로젝트에 넣지 말 것)
   ```
3. **코드와 PDF만 남긴다** — `_build/`, 이미지, 스크린샷, html, 원본 과제 PPT 등 삭제. **최종 PPTX는 지우기 전에 사용자에게 확인**
4. 중복 폴더 삭제 (임시 작업 폴더, `C:\Temp\...` 등) — 복사본이 원본과 같은지 확인한 뒤 지운다
5. Vivado 프로젝트가 옮긴 파일을 참조하고 있으면 **새 경로를 사용자에게 알려준다**

## 10. 이 가이드라인 업데이트 규칙

- 프로젝트가 끝나면 사용자 피드백 + Claude 피드백을 합쳐 이 md를 갱신한다. 목적: **다음 Claude가 이 문서만 보고 바로 PPT를 만들 수 있게.**
- 프로젝트별 진행 기록(슬라이드 번호, 점수, 파일명 등)은 남기지 않는다. **다른 과제에도 적용되는 규칙·교훈만** 해당 섹션에 녹여 넣는다.
- 끝난 프로젝트 폴더(예: `8bit_fnd_clk_project/`)는 참고 대상이 아니다. 새 과제는 새로 올라온 PPT 기준으로 진행한다.

## 체크리스트 (제출 전)

- [ ] 슬라이드에 코드 조각이 없다. 모듈 이름·설계 용어는 영어 그대로, 덱 전체 통일
- [ ] 구조 설명은 2단(실제 구성 / 쉬운 풀이), "왜"가 한 줄씩 있다
- [ ] 파형 슬라이드가 §3-1 표시 방식을 따른다
- [ ] 원본 PPT와 코드가 다른 부분을 코드 기준으로 고치고 보고했다
- [ ] 숫자는 실측했거나 추정이라고 밝혔다
- [ ] 검증 방법론 평가 + 결함 주입 증거가 있다
- [ ] 사용자가 직접 고친 부분이 유지됐고, 슬라이드 위 요청 메모는 지웠다
- [ ] 페이지 번호·페이지 참조가 맞다
- [ ] PowerPoint로 열어 전 슬라이드 QA를 했다
- [ ] Verilog 파일은 영어 주석, `homework/<프로젝트명>/`에 있다
