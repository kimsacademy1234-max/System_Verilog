## 1. 왜 TB에 "검사기"를 만드나

- 지난번 시뮬레이션: 버튼 → TX 출력을 **눈으로** 파형 확인
- 오늘 목표: TB 안에 소프트웨어 수신기를 만들어 **보낸 값 = 받은 값** 자동 판정
  - 같으면 PASS, 다르면 에러 메시지 출력
  - start / stop / baud rate 에러 종류까지 자동 검사 가능
- 검증 방법 두 가지
  - **SW 검사기**: TB 안에서 baud time 계산해 직접 샘플링 → 설계가 덜 됐어도 타이밍 틀어짐 측정 가능
  - **HW 송수신**: TX·RX 둘 다 만들어 서로 주고받기 → 설계가 다 됐을 때 가능
- 확장 아이디어: 노이즈 주입, 클럭 주기 흔들기(5ns → 4.5/5.5ns), 패턴 변경, 미사용 로직 검출
  - 이를 표준화·자동화한 것이 **UVM**

### 전수 검사 vs 경계값
- 8bit 데이터 = 256가지 + start/stop bit 일부러 깨뜨린 에러 케이스까지 조합
- 랜덤 패턴 전송 → 특정 값/특정 비트 위치에서만 나는 버그 검출
- 사람이 하는 검증은 정상 1~2개 + **경계값**만 확인 (규칙적으로 동작한다는 가정)
- 비트 폭이 32bit 등으로 커지면 수작업 전수 검사 불가 → **프로그램으로 검사** = UVM의 존재 이유

## 2. task vs function

| 구분 | function | task |
|---|---|---|
| 반환 | return 값 있음 | 없음 (output 포트 사용) |
| 출력 포트 | 없음 | 있음 (모듈 포트처럼) |
| **시간 제어** (`#`, `@`, `wait`) | **불가** | **가능** ← 결정적 차이 |
| 용도 | sin/π 같은 순수 계산 | 시간 흐름이 필요한 동작 |

- RX 검사기는 **일정 시간(baud time)마다 delay 주며 읽어야** 하므로 → **task**
- 교수님은 Verilog에서 function 거의 안 씀 (task로 다 가능, 개인 스타일)
- task는 자기 모듈 안 변수에 직접 접근 가능 → 인자 생략 가능

## 3. TB 수신 task (TX 출력 검사기)

### 3-1. 샘플링 시점: 왜 비트 중앙인가
- UART는 **클럭(동기 신호)이 없음** → 아는 건 TX 신호와 시간뿐
- 데이터가 바뀌는 **transition 근처**에서 읽으면
  - 실제 HW: **메타스테이블** 발생 가능
  - start bit / bit0 / bit1 구분이 흔들림
- **중앙**에서 읽으면 가장 안정적, 송신 쪽이 조금 당겨지거나 밀려도 문제없음
- 시뮬레이터는 시간이 완벽히 일정하지만 실제 HW는 아님 → 시뮬레이션 ≠ 실제
- 예시: TX에 start WAIT 없이 보냈을 때 같은 값이 가끔 다른 값으로 인식됨 → 첫 비트가 짧아져 수신 쪽 샘플 시점이 경계에 걸린 것

### 3-2. 타이밍 시퀀스

```
TX: ‾‾‾‾\____|_D0_|_D1_|...|_D7_|‾STOP‾
         ↑  ↑    ↑    ↑         ↑    ↑
     감지 1/2T  +T   +T  ...   +T   +T
          (start 확인) (D0)          (stop 확인)
```

1. `wait (tx == 0);` — start 감지
2. `#(BAUD_BIT_PERIOD/2);` → start bit 중앙에서 `tx == 0` 재확인
3. `for (i = 0; i < 8; i++)` : `#(BAUD_BIT_PERIOD);` 후 `rx_data[i] = tx;` (**LSB부터**)
4. `#(BAUD_BIT_PERIOD);` → stop bit `== 1` 확인
5. 기대값과 비교 → `$display` PASS / FAIL (또는 `$error`)

- 방식 선택: "매 비트 1/2T + 1/2T" 대신 **처음만 1/2T, 이후 계속 1T** → 자동으로 계속 중앙 유지

### 3-3. `@(negedge tx)` 대신 `wait (tx == 0)` 쓰는 이유
- 버튼 누르자마자 TX가 이미 출발하면, task 호출 전에 **edge를 놓칠 수 있음**
- edge를 놓치면 다음 edge까지 무한 대기 → **시뮬레이션 멈춤**
- 타임아웃 탈출 조건 넣기 번거로우니 **레벨(0) 검사**로 안전하게

### 3-4. 실습 중 나온 이슈
- **edge를 이미 지나간 뒤 wait** → 영원히 안 걸림
  - DUT/TB 구성이 교수님과 달라 TX 신호가 task 호출 전에 끝나버린 경우
  - 해결: 모듈 내부 TX 신호를 **직접 참조**(hierarchical)해서 읽기
- **기대값 0x30인데 0x04 수신** → TB 문제가 아니라 **설계 미스**
  - 확인 순서: ① baud tick 주기 (1bit = **104.16 µs** 맞는지) ② state 전이
  - FSM을 data count 방식으로 바꾼 뒤 재검증 안 한 경우가 원인
- **Vivado 시뮬 재실행 불가**: 브레이크포인트 디버깅 중 멈추면 sim 디렉터리의 **`simulate.log`를 잡고 놓지 않음**
  - 해결: 시뮬 디렉터리에서 해당 log 파일 삭제 후 재실행 (지워도 무방)
- PASS/FAIL 출력은 **Tcl Console**에서 확인
- 디버깅: 소스에 브레이크포인트 → 한 줄씩 진행 가능 (교수님은 잘 안 씀)

## 4. 비동기 수신 이론 — 왜 16배 오버샘플링인가

### 4-1. 100MHz로 계속 감시하면?
- 장점: 중앙을 정확히 찾을 수 있음
- 문제: 외부 디바이스에서 날아오는 신호 → **노이즈 + 비동기 transition**
  - 매 클럭 읽을수록 transition/노이즈 순간에 걸릴 기회 증가 → **메타스테이블 확률↑**
  - 1bit 동안 샘플 수: 104.16 µs × 100 MHz ≈ **10,416번** *(계산)* vs 16배 tick이면 **16번**
- 메타스테이블 대응 원칙
  1. **발생 확률 자체를 낮춘다** → 필요한 순간에만 tick으로 샘플링
  2. 발생해도 받을 수 있게 → **synchronizer**(2-FF) 추가
- 교수님 경험: 확률만 낮춰도 synchronizer 없이 에러 거의 없음 (100%는 아님)

### 4-2. tick 배속과 틀어짐
- b_tick = baud tick × 1이면, RX 입력과 tick 위상이 안 맞음 → 중앙 보장 불가
- 배속을 올릴수록 start 감지 오차 감소

| 배속 | 최대 위상 오차 (1bit 대비) |
|---|---|
| ×1 | 최대 100% |
| ×2 | 50% |
| ×4 | 25% |
| ×8 | 12.5% |
| **×16** | **6.25%** |

- 배속↑ 단점: 메타스테이블 확률↑, 카운터 비트 수↑ (로직 증가) → **trade-off**
- 권장: **최소 8배 ~ 16배**, 8배는 다소 위험 → **16배로 설계**

### 4-3. TI MSP430 UART 앱노트 정리 (교수님 배포 자료)
- 구조: TX는 **PISO**, RX는 **SIPO**
- Common baud rate: 9600, 19200, 115200 …
- 일반적인 최대 baud rate 오차 허용: **2~3%**
- 16배 오버샘플 클럭 사용 (우리 16배 b_tick과 본질적으로 동일)
- 마진 계산
  - 이상적 마진 50% (비트 중앙)
  - − 16배 샘플링 오차 6.25% (1/16)
  - − rise/fall 오차 2%
  - = **실제 마진 41.75%**
  - 10bit 프레임 누적 고려 → 송·수신 각각 **±4.175%**까지 허용 *(계산: 41.75 / 10)*
- 틀어짐은 **비트마다 누적** → 마지막 비트에서 가장 커짐, 그래도 마진 안이면 OK
- 자료는 외부 배포 금지 (저작권)

## 5. 16배 b_tick 변경

- `F_COUNT = 100MHz / (9600 × 16)` ≈ **651** *(계산)*
- tick 주기 = 104.16 µs / 16 ≈ **6.51 µs** *(계산)* → 시뮬레이션에서 tick 간격 측정해 확인
- 이 변경 이후 기존 TX는 16배 빨라져서 틀어짐 → TX도 수정 필요

## 6. UART RX 설계

### 6-1. 상태
**IDLE → START → DATA → STOP → IDLE**

| 상태 | 동작 | 전이 조건 |
|---|---|---|
| IDLE | b_tick마다 rx 확인 | `b_tick && rx == 0` → START |
| START | b_tick_cnt 0~7 카운트 (**8 tick = 1/2 bit**) | cnt == 7 → start 재확인 (`rx == 0`) → DATA, 아니면 IDLE/에러 |
| DATA | b_tick_cnt 0~15 카운트 (**16 tick = 1 bit**) | cnt == 15 → rx 샘플 & shift → bit_cnt == 7이면 STOP, 아니면 bit_cnt++ 후 DATA |
| STOP | 16 tick 카운트 | cnt == 15 → `rx == 1` 확인 (아니면 frame error) → rx_done 펄스, IDLE |

### 6-2. 설계 포인트
- 카운트는 **0부터** → 8개면 0~7, 16개면 0~15
  - bit_cnt 0~7은 **3bit** (8로 세면 4bit 필요)
- 읽는 순서: **16 tick 카운트 → 읽기 → bit_cnt 처리** (증가 먼저 하면 안 됨)
- 수집 구조: **SIPO shift register**, LSB부터 들어옴
  - 예: `rx_data_next = {rx, rx_data_reg[7:1]};`
- 카운터 초기화: 상태가 넘어갈 때마다 b_tick_cnt를 0으로 (START 진입, START→DATA, DATA 비트마다, DATA→STOP)
- STOP 처리 선택
  - 16 tick 끝까지 가서 판정, 또는
  - stop bit 중앙에서 판정 후 바로 IDLE로 빠져 **다음 프레임 준비** (교수님 선호)
- 출력
  - **rx_done**: 수신 완료 시점에 **1 tick 펄스** (CPU/후단 로직에 알림)
  - "수신 중(busy)" 신호는 RX에선 중요도 낮음 (넣어도 무방)
  - 에러 신호: start/stop 검사 실패 시 띄움

## 7. UART TX 수정 (16배 tick 대응)

- **WAIT 상태 제거**: tx_start → IDLE에서 바로 START
  - 이유: 최대 1/16 bit(6.25%) 일찍 시작해도 **최초 1회만** 발생, 누적 아님 → 수신 측 문제없음
- b_tick_cnt 추가 (16 tick = 1 bit, 4bit 레지스터) → reset 초기화에도 추가
- 상태별 전이: 각 상태에서 `b_tick && b_tick_cnt == 15`일 때 다음 단계
- DATA: 16 tick마다 data reg 1bit shift, bit_cnt == 7이면 STOP
- STOP: 16 tick 후 IDLE
- **tx_busy**: START 진입 시 1, IDLE 복귀 시 0
- 공통 초기화(b_tick_cnt = 0)는 앞으로 빼서 중복 제거
- START → DATA 전이 시 카운터 초기화 누락 주의 (실습 중 빠졌던 부분)
- 체크: next/reg 뒤바뀐 곳 없는지, latch 생성 없는지 RTL 확인

## 8. Loopback 구성 (보드 검증)

### 8-1. Top (`uart.v`)
- 버튼 디바운서, LED 제거
- **RX → TX 직결 구조**
  - `rx_done` → `tx_start`
  - `rx_data[7:0]` → `tx_data`
- tx_busy 대기 불필요 (컨트롤러 없이 받는 즉시 보내는 구조)

### 8-2. XDC
- USB-UART **RX/TX 핀 주석 해제**
- 버튼은 **reset만** 남기고 주석 처리, LED 주석 처리, clock 유지
- Bitstream 생성 시 에러 없어야 함

### 8-3. 보드 테스트
- 장치 관리자에서 COM 포트 확인 → ComMaster로 open
- 1글자 보내면 1글자, 2글자면 2글자, **연속 데이터도 문제없이** 돌아와야 함 (ASCII 그대로)
- 글자가 깨지면 → **비트 밀림** → 시뮬레이션으로 원인 추적

## 9. Loopback TB

- DUT: loopback top, `rx`는 TB에서 구동하므로 **reg**, 초기값 **1** (idle)
- **sender task** (PC → FPGA RX 역할)
  1. `rx = 0;` → `#(BAUD_BIT_PERIOD);` (start bit은 **1/2이 아니라 1비트 전체**)
  2. 8번 반복: `rx = send_data[i];` → `#(BAUD_BIT_PERIOD);` (LSB부터)
  3. `rx = 1;` → `#(BAUD_BIT_PERIOD);` (stop)
- **receiver task**: 3장 검사기를 DUT `tx`에 연결
- 예: expected = `8'h30` 보내고 받은 값 비교 → Tcl Console에 PASS
- 파형에 추가할 신호
  - RX: state, b_tick_cnt, bit_cnt, data reg, rx_done
  - TX: tx_start, tx_busy, state, bit_cnt, b_tick_cnt, data reg, tx
- 실습 중 이슈: sender 쪽 포트 방향(output/input) 잘못 연결 → RX가 안 올라옴

## 12. 복습 Q&A (수업 후 의문점 정리)

### Q1. 16배 오버샘플링을 하는 이유
- RX는 TX 클럭을 모름 → start bit 시작 시점을 **자기 tick으로 직접 찾아야** 함
- **① start 감지 정밀도 = 1/N bit**
  - tick이 올 때만 rx를 보므로 실제 하강 시점 대비 최대 1 tick 늦게 감지
  - ×16 → 최대 1/16 bit(6.25%) 지연 → 8 tick 후 샘플 시 비트의 50~56.25% 지점
- **② 남는 마진으로 baud 오차 흡수**
  - PC·FPGA baud 차이가 비트마다 누적, stop bit은 감지 후 약 9.5 bit 뒤 샘플
  - 마진 = 50% − 감지 오차 − rise/fall 2%

| 배속 | 감지 오차 | 마진 | 허용 baud 오차 (≈ 마진/10) |
|---|---|---|---|
| ×4 | 25% | 23% | ±2.3% |
| ×8 | 12.5% | 35.5% | ±3.5% |
| **×16** | **6.25%** | **41.75%** | **±4.2%** |
| ×32 | 3.1% | 44.9% | ±4.5% |

  - ×4는 일반 클럭 오차(2~3%)에 빠듯, ×32는 이득 0.3%p뿐인데 카운터·toggle 증가 → **×16이 적정점**
  - 8250/16550 등 전통 UART 칩도 16배 클럭 사용
#### 보충: 마진이란
- **샘플 지점이 중앙에서 얼마나 벗어나도 아직 같은 비트 안인지**를 나타내는 여유 폭, 넘으면 옆 비트를 읽음
- **1단계 — 처음 여유 50%**: 정중앙에서 읽으면 양쪽 경계까지 각각 반 비트

```
        |←────── 1 bit (100%) ──────→|
  ──────X═════════════════════════════X──────
     경계            ↑ 중앙            경계
        |←── 50% ──→|←──── 50% ────→|
```

- **2단계 — 이미 써 버린 몫 빼기**
  - 감지 오차 6.25%: start를 최대 1 tick 늦게 감지 → 출발부터 샘플 지점이 중앙보다 최대 6.25% 뒤
  - rise/fall 2%: 실제 신호는 기울기가 있어 경계 근처는 값이 애매 → 사용 불가 구간
  - 50 − 6.25 − 2 = **41.75%** = 아직 아무것도 안 쓴 여유
- **3단계 — baud 차이가 비트마다 누적해서 마진 소모**
  - 예: PC가 1% 빠르면 RX는 매 비트 1%씩 TX보다 늦게 읽음

| 샘플 | start | D0 | D1 | … | D7 | stop |
|---|---|---|---|---|---|---|
| 감지 후 경과 | 0.5 bit | 1.5 | 2.5 | … | 8.5 | 9.5 |
| 누적 밀림 (1% 차이) | 0.5% | 1.5% | 2.5% | … | 8.5% | **9.5%** |

  - 가장 먼 **stop bit**에서 밀림 최대 → 이게 41.75% 안이면 전 비트 정상 수신
  - 허용 baud 오차 ≈ 41.75 ÷ 10 ≈ **±4.2%** (정확히는 9.5 bit, 앱노트는 10 bit로 보수적 계산)
- 엄밀히는 비대칭: 감지 오차는 항상 늦는 쪽 → TX가 빠른 쪽 여유가 더 작음, 앱노트는 최악값을 양쪽에 동일 적용
- 요약: **감지 오차 = 출발점의 틀어짐, 마진 = 그걸 빼고 남아 baud 차이에 쓸 수 있는 여유**

- **③ 구현 용이**: 4bit 카운터 0~15 자연 wrap, 중앙 8도 딱 떨어짐
- 주된 이유는 메타스테이블이 아니라 **타이밍 정밀도와 마진** (메타스테이블은 synchronizer로 해결, Q6)

### Q2. PC도 9600으로 보내고, FPGA는 정밀하게 보려고 baud rate를 올리는 것인가
- **baud rate는 양쪽 모두 9600 그대로**, 올리는 건 FPGA 내부 **샘플링 tick**(153.6 kHz = 9600 × 16)
  - 1초짜리 비트를 1/16초 눈금 자로 재는 것, 대상 길이는 그대로
- PC가 원래 9600인 게 아니라 **터미널(ComMaster)에서 9600, 8N1로 설정**했기 때문
  - 실제 UART 파형은 보드의 **FTDI USB-UART 칩**이 설정값으로 생성
  - FPGA는 `uart.v`에 9600 고정 → 설정 불일치 시 글자 깨짐
- 단위: 9600은 Hz가 아니라 **bps(baud)**, 1 bit = 104.17 µs, 1글자 10 bit → 최대 960 글자/s
  - 0101 반복 파형이면 한 주기에 2 bit → 실제 주파수 4800 Hz
- 실제 오차 *(계산)*
  - FPGA: F_COUNT 651.04 → 651, tick 153,610 Hz → baud 약 9600.6 (+0.006%)
  - TB: `100_000_000 / 9600 * 10` = 104,160 ns (이상값 104,166.7 ns 대비 −0.006%)
  - 허용 ±4.2% 대비 무시 가능 수준. 단 115200 등 고속에선 분주 오차 커지므로 재계산 필요

### Q3. 오늘 설계 = TX는 15에서 다음 비트, RX는 7에서 start 샘플 후 15마다 중앙 샘플?
- **맞음.** 실제 `uart_rx.v` 구조와 일치

| | 조건 | 의미 |
|---|---|---|
| TX | `b_tick_cnt == 15` (16 tick) | 1 bit 길이 채우고 다음 비트 출력 |
| RX START | `b_tick_cnt == 7` (8 tick) | start bit 중앙 → DATA |
| RX DATA | `b_tick_cnt == 15` (16 tick) | 다음 비트 중앙에서 `data_next = {rx, data_reg[7:1]}` |
| RX STOP | `b_tick_cnt == 15` | stop bit 중앙 → `rx_done` 1클럭 펄스, IDLE |

- "7"은 0~7 = **8 tick**, "15"는 0~15 = **16 tick** (0부터 카운트)
- 비트당 **한 번만** 읽음, 16배 tick은 중앙 위치를 찾기 위한 눈금
- 현재 코드에 빠진 것
  - **START 재확인 없음**: 8 tick 지점 `rx == 0` 미확인 → 노이즈로 false start 가능
  - **STOP 확인 없음**: `rx == 1` 미확인 → frame error 미검출

### Q4. tick을 안 올리고 RX 1x 클럭 위상을 90°로 맞추면 안 되나
- **안 됨 — 위상을 맞출 기준이 없음**
  - UART는 클럭선 없음, start bit 시점이 매 프레임 임의 → RX 클럭과 데이터 위상이 프레임마다 랜덤
  - 고정 위상 오프셋으로는 중앙 보장 불가

```
RX 1x clk : |‾‾‾‾|____|‾‾‾‾|____|‾‾‾‾|____|
TX 1회차  :   ‾‾‾\______________          ← 중앙 근처
TX 2회차  :   ‾‾‾‾‾‾‾‾‾\_________          ← 경계 근처
```

- 매 프레임 start edge 기준으로 재정렬하려면 edge를 **1x보다 빠르게** 봐야 함 → 그 자체가 오버샘플링
  - 16배 tick → 오늘 설계
  - 100 MHz로 edge 감지 후 baud 카운터 리셋, 반 비트 카운트 → 교수님이 말한 "런/스톱 제어" 방식 (실무에서도 사용)
  - MMCM 위상 조절은 한 단계씩 느리게 움직여서 프레임마다(약 1 ms) 재정렬하는 용도로 불가
- 각도도 **90°가 아니라 180°** (비트 경계 0° 기준 중앙 = 반 비트)
- 90° 시프트가 맞는 경우: **DDR 같은 클럭 동반(source-synchronous) 인터페이스**
  - 반 주기마다 데이터가 바뀌므로 90° = 데이터 한 칸의 중앙 (DDR 메모리의 DQS 90° 시프트)
  - 같이 오는 클럭이라는 **기준이 있어서** 가능, UART는 기준이 없어서 스스로 찾아야 함

### Q5. 하필 중앙(8번째 tick) 샘플 순간에 데이터가 흔들리면?
- 단일 샘플이라 그 순간 노이즈가 튀면 **그 비트는 틀림** — 실제로 생길 수 있는 문제
- 구분
  - 마진이 맞다면 중앙에선 정상 transition 없음 → 중앙의 흔들림 = **노이즈(glitch)**
  - **메타스테이블 위험이 큰 곳은 IDLE의 start 감지** (rx 하강 시점이 임의라 transition 순간에 걸릴 수 있음)

| 방법 | 막는 것 | 구현 |
|---|---|---|
| ① 2-FF synchronizer | 메타스테이블 | rx를 100 MHz FF 2단 통과 후 사용 |
| ② 3점 다수결 | 중앙 순간 노이즈 | 중앙 근처 tick 3개(7·8·9번째) 중 2개 이상 값 채택 (STM32 방식, 불일치 시 노이즈 플래그) |
| ③ start 재확인 | glitch에 의한 가짜 start | 8 tick 지점 `rx == 0` 재확인, 아니면 IDLE |
| ④ stop / parity 검사 | 검출 (복구 X) | frame error / parity error → 상위에서 재전송 |
| ⑤ glitch filter | 아주 짧은 스파이크 | 100 MHz에서 N클럭 연속 같은 값일 때만 인정 |

```verilog
// ② 다수결 스케치: b_tick마다 rx 이력 3개 저장
reg [2:0] rx_hist;
always @(posedge clk) if (b_tick) rx_hist <= {rx_hist[1:0], rx_sync};

// 3개 중 2개 이상이면 1
wire rx_vote = (rx_hist[0] & rx_hist[1]) | (rx_hist[1] & rx_hist[2]) | (rx_hist[0] & rx_hist[2]);
// DATA에서 data_next = {rx_vote, data_reg[7:1]};
```

- 이렇게 하면 3샘플 중심이 원래보다 1 tick 앞당겨짐 → 신경 쓰이면 START를 `cnt == 8`로 1 tick 늘려 보정
- 결론: 확률 낮추기(16배 tick, 중앙 샘플링)만으로는 0이 안 됨 → ① 메타스테이블, ② 노이즈 차단, ③④ 남은 에러 검출

### Q6. async 입력은 앞에 synchronizer 붙이면 해결?
- **1비트 비동기 입력**이면 2-FF synchronizer가 표준
- 해결하는 것: **메타스테이블**
  - 1단 FF가 메타스테이블에 빠져도 1클럭(10 ns) 안정 시간 → 2단이 안정된 값 전달
  - 확률 0은 아니지만 평균 고장 간격(MTBF)이 수백~수천 년으로 늘어남 → 사실상 해결
  - 대가: 2클럭 지연 (1 bit = 10,416클럭이라 무시 가능)
- 해결 못 하는 것

| 문제 | 이유 | 대응 |
|---|---|---|
| 노이즈 / glitch | 노이즈도 유효한 0/1로 깔끔하게 동기화해 넘김 | 다수결, glitch filter |
| 데이터 오류 | 값 자체가 틀린 건 못 고침 | parity, stop 검사 |
| **멀티비트 버스** | 비트별 동기화 클럭이 1클럭씩 어긋나 **값이 섞임** | handshake, Gray code, async FIFO |

- 면접 함정: "8bit 버스에 비트마다 2-FF 달면 되나?" → **안 됨**
  - 예: `0111 → 1000`처럼 여러 비트가 동시에 바뀌면 일부만 새 값으로 잡혀 `1111` 같은 엉뚱한 값 가능
- UART RX 적용: rx는 1비트 → 2-FF로 충분, 현재 `uart_rx.v`는 rx를 FSM에 바로 사용 중 → 추가 필요

```verilog
reg rx_sync1, rx_sync2;
always @(posedge clk) begin
    rx_sync1 <= rx;
    rx_sync2 <= rx_sync1;
end
// FSM에서는 rx 대신 rx_sync2 사용
```

- reset 시 두 FF를 **1(idle)로 초기화** (0이면 가짜 start로 오인)

#### 보충 1: synchronizer 2단 지연 때문에 마진이 줄어드나?
- **안 줄어듦**
- ① 지연은 2 tick이 아니라 **2클럭(100 MHz)** = 20 ns → 1 bit(104,167 ns) 대비 **0.02%**, b_tick 1개(6,510 ns)보다도 훨씬 작음
- ② 더 근본적으로, **모든 비트가 똑같이 밀리는 고정 지연은 마진을 먹지 않음**

```
원래 rx    : ‾‾\_start_|_D0_|_D1_| ...
sync 후 rx : ‾‾‾\_start_|_D0_|_D1_| ...   ← 파형 전체가 20 ns 평행이동
                ↑ 감지      ↑ 샘플
```

  - start 감지와 데이터 샘플 **둘 다 `rx_sync2` 기준** → 감지·샘플 모두 20 ns 늦어짐 → 동기화된 파형 위에서 여전히 정중앙
  - 마진을 먹는 것은 **비트마다 쌓이는 오차**(baud 차이)와 **출발점의 불확실성**(감지 오차)뿐
- 설령 2 tick(12.5%)이어도 고정 지연이라 마진은 그대로, `rx_done`이 늦게 나오는 **latency 증가**만 발생
  - 감지 오차 6.25%의 원인은 지연이 아니라 **1 tick 안 어디서 감지될지 모르는 불확실성**
- 요약: **고정 지연 → latency만 증가 / 불확실성·누적 오차 → 마진 감소**

#### 보충 2: synchronizer는 왜 b_tick이 아니라 100 MHz로 돌리나?
- 핵심: **이 설계의 클럭은 100 MHz 하나뿐, b_tick은 클럭이 아님**
- ① **b_tick = enable 펄스**

```
clk    : _|‾|_|‾|_|‾|_|‾|_|‾|_|‾|_ ... (100 MHz, 계속 돎)
b_tick : ____|‾‾‾|____________ ... ____|‾‾‾|____   (651클럭에 1번, 1클럭 폭)
```

  - FSM·카운터·data 레지스터 모두 `always @(posedge clk)` → **100 MHz 동작**, b_tick은 "이번 클럭에 일해라" 허가 신호
  - 메타스테이블은 **rx를 받는 FF의 클럭 edge**에서 발생 → 그 FF가 100 MHz이므로 synchronizer도 100 MHz
  - 원칙: synchronizer는 **신호를 받아 쓰는 쪽(목적지) 클럭**으로 구동
- ② **b_tick을 클럭으로 쓰면 안 되는 이유**
  - 카운터 로직이 만든 신호 → `posedge b_tick`은 gated/derived clock
  - 클럭 전용 배선(BUFG) 미사용 → FF마다 클럭 도착 시간 차이(skew)
  - 로직 출력이라 glitch 시 클럭이 한 번 더 들어간 것처럼 동작 가능
  - Vivado 타이밍 분석 복잡·불완전
  - FPGA 기본 원칙: **클럭은 하나, 느린 동작은 tick enable** (stopwatch, UART에서 써 온 방식)
- ③ **100 MHz면 안정 시간 충분**
  - 1단 FF에 1클럭 = 10 ns 안정 시간 부여, 최신 FPGA FF는 대부분 수백 ps 내 안정
  - 실패 확률은 안정 시간에 지수적으로 감소 → 10 ns면 사실상 0, 지연도 20 ns로 최소
- Vivado 속성

```verilog
(* ASYNC_REG = "TRUE" *) reg rx_sync1, rx_sync2;
```

  - 두 FF를 같은 slice에 배치 → 사이 배선 지연 최소화 → 안정 시간 최대
  - synchronizer임을 툴에 표시 → 타이밍 리포트에서 구분
- 요약: **rx를 받는 FF가 100 MHz → synchronizer도 100 MHz, b_tick은 enable이라 클럭으로 쓰면 오히려 문제**
